# Butter: independent opinion on long-chat scrollbar responsiveness

**Trade-off — Verdict:** **A wins the release decision:** keep the alpha.9 scope, retain the history rail as the fast navigation route, and stop expanding the mounting/layout intervention. The desired outcome, **X**, is predictable, responsive travel through a long chat without sacrificing typing or streaming. No tested treatment delivers that outcome through continuous native-thumb dragging. Shipping B as “the scrollbar fix” would overstate a partial improvement; replacing the native thumb with C would exchange a demonstrated performance problem for an unmeasured interaction and accessibility problem. This recommends a release scope; it does not certify an alpha.9 package.

**Conditional — Best next experiment:** test **D1, an additive question scrub gesture on the existing rail**, with destination preview while held and one logical destination committed on release. Keep the native scrollbar available. This borrows C's useful mechanism without first taking responsibility for replacing every native scrollbar behavior. Promote D1 over A only if users actually prefer it and paired measurements preserve streaming. No implementation or lab experiment was performed for this opinion.

**Unverified — User-intent boundary:** “snappy native scrollbar” might mean continuously seeing actual answer content beneath a dragged native thumb, including arbitrary positions inside a very long answer. If that behavior itself is non-negotiable, the XY reframe does not satisfy the request: **none of A–D is a demonstrated complete solution under the present constraints**. The recommendation then becomes an honest limitation plus upstream work, rather than claiming that a rail is equivalent.

## X, Y, and the XY finding

**Conditional — One-sentence frame:** assuming the user's underlying need is fast, understandable history navigation (**X**), making ChatGPT's native scrollbar continuously drag through newly mounted giant turns by changing mounting/layout (**Y**) is one possible treatment, constrained by an extension's lack of a supported ChatGPT renderer API, changeable private integration points, mandatory streaming safety, and one maintainer.

**Trade-off — XY finding:** this is a **partial XY problem**. Y is a direct route if continuous native content scrubbing is the requirement. It becomes an overly narrow route if the real job is “get back to the answer/question I want without losing control.” Evaluate semantic navigation as a competing treatment, while explicitly preserving the unresolved within-answer/native-drag requirement. A preview followed by a jump changes the interaction contract; it does not make native dragging faster.

**Verified — Existing seam:** the rail already obtains question identities/text from ChatGPT's existing responses, previews questions, and supports buttons plus arrow-key navigation. Its `jump`, `estimate`, `depart`, `steady`, `follow`, `cancelJump`, and `loadEarlier` functions implement estimated placement, target discovery, readiness checks, cancellation, and placeholder animation. They do not expose an independent content renderer. A “single jump” is one user commitment, **not necessarily one scroll write or one React commit**: `jump` may retry placement eight times, wait for math/pages, and keep correcting geometry. [L0, `butter-nav.js`, especially lines 478–733]

**Trade-off — Verdict-changing constraints:**

- **Verified:** Butter's principal interventions are a narrowly matched stream-smoother throttle, CSS container override, seen-gated content visibility, and smaller existing history requests. Extra connected active DOM and large generated rule sets have already materially regressed streaming. [L0–L3, L5–L6]
- **Conditional:** a treatment that needs a maintained fork of ChatGPT's private virtualizer or bundle-response rewriting is not competitive for this extension unless a supported seam appears. The research CDP rewriting is not proof of a deployable MV3 integration. [L1–L2]
- **Trade-off:** one maintainer makes platform input/accessibility parity and global prototype hooks substantial ongoing costs. Existing private integrations are not a reason to prohibit every new one; judge the incremental blast radius. A DOM-scoped preview is narrower than wrapping every `Element.clientWidth` call or replacing the primary scrollbar.
- **Conditional:** unknown message heights, content-width changes, regenerated answers, cold math/fonts, missing pages, and SPA navigation must fall back to accurate native behavior rather than invented geometry. If the fallback is slow, that is a latency limit, not evidence the guard should be removed. [L3, L5–L6]

## Diagnosis check: what the local evidence actually establishes

**Verified — Mechanism in plain language:** ChatGPT keeps a moving group of conversation turns in the DOM. A long math answer is one enormous item, not thousands of independently mountable lines. Dragging the browser's thumb can move the viewport to a place for which ChatGPT has not built those turns yet. React then creates the new DOM; a collapsible-text ref asks for `clientWidth` during commit, forcing Chrome to calculate layout immediately. The saved ref also uses computed style and conditionally `scrollHeight`. Butter's later MutationObserver cannot go back in time and protect that first read. Caching block geometry before the native read makes part of this work cheaper; it does not eliminate DOM creation, styling, rendering activation, or the first measurement of unknown content. [L1, L3; saved module `oQwr` in `396705.cd1656e9ad.js`]

## Issues, ranked by consequence

### 1. A / C / D1 — losing the actual navigation requirement

**Trade-off — Where:** replacing an exact native spatial interaction with question navigation. **Trigger:** the user wants a formula halfway through a 34k px answer, or scans visually until recognizable content passes. **Consequence:** a question preview plus jump may be responsive yet fail the task. **Evidence:** the current rail indexes question IDs, not arbitrary answer offsets; its documented far jumps take around 1–2 seconds on the test machine and sometimes around 6 seconds on opening. [L0] **Fix:** evaluate actual tasks separately: known-question retrieval, unknown-content scanning, and within-answer positioning. Keep native scrolling for the latter two. Do not rename a question scrubber “a faster native scrollbar.” Cost is a small task study; verify by successful target retrieval, not preference alone.

### 2. B / D2 — wrong geometry during the commit being optimized

**Conditional — Where:** cached block fallback restoration before the getter. **Trigger:** sidebar resize changes content width while `innerWidth` stays fixed; a hidden chat contributes measurements under another URL; answer content changes while counts/shapes still appear compatible; math/fonts finish late. **Consequence:** React measures a wrong turn height, position correction follows, and destination/scrollbar geometry can move. **Evidence:** the **actual best prototype** uses `conv()` from `location.pathname`, a turn-key map, exact `innerWidth`, assistant-message identity, block count, and math readiness. It records content width but does not compare that width before restore. Its getter's narrow filter is DOM shape, not a pinned stack/source signature. [L3, `extension-best/remount-prototype.js:9–26`] The previous cache's width/identity/owner failures were directly reproduced in fixtures. [L6] **Fix:** stable DOM-owner conversation/message/revision identity, a synchronous exact content-width applicability guard, completed/typeset samples, and pass-through on every uncertainty. A later ResizeObserver cannot guard an earlier read. Verify same-task width changes, hidden chats, answer replacements, and natural-height equality. This is new correctness work; it is not already solved by the warm drag numbers.

### 3. C — reliable interception is not established

**Conditional — Where:** obtaining an ordinary page pointer gesture from native scrollbar dragging. **Trigger:** the browser takes the native gesture before Butter does, uses an overlay gutter with no layout width, places the gutter left in RTL, or changes the hit area under OS preferences/zoom. **Consequence:** both controls can move, the overlay can miss, or content hit targets can be stolen. **Verified evidence:** the hold experiment receives native down/up but **no native move events**; its overlay hit-test fallback is a 12 px edge heuristic. That establishes hold detection in one lab, not a portable cancelable native drag API. [L4] CSS's deliberate platform limits corroborate the portability concern. [E10] **Fix:** a real Butter-owned hit target before pointerdown, or D1 outside the native gutter. Test pointer capture, outside-window release, cancellation, RTL, zoom, overlay and always-visible OS bars. If native takeover cannot be disabled without side effects, reject interception rather than suppressing scroll events after it begins.

### 4. C / D1 / D2 — smooth preview hides a release freeze

**Conditional — Where:** release handler and existing `jump`/readiness machinery. **Trigger:** a cold destination requires a huge React commit, math, or older pages. **Consequence:** the pointer preview feels good, but release-to-useful-content still takes seconds and can block unrelated input. If streaming already occupies the main thread, the JS-driven preview itself can lag too. **Evidence:** suppressed-scroll release frame 2,383.3 ms; B retains second-scale warm frames; the rail code can retry mounts and keeps a 12-second ordinary trip deadline. [L0–L3] **Fix:** keep the current page stable while previewing, start no target renders until commitment, use compositor-driven pending feedback, reveal only when settled, and measure actual readable destination plus key latency. Deadline/cancellation must restore content even after failure. “One logical jump” may need several internal corrections; record them and all commits. A release-only design improves navigation during the hold, not necessarily final latency.

### 5. C — native access and platform behavior become Butter's responsibility

**Conditional — Where:** hiding/replacing the browser's primary thumb. **Trigger:** keyboard or assistive-technology use, high-contrast/forced colors, coarse pointers, OS enlarged controls, track clicks, trackpad/wheel input, or Windows off-track drag reset. **Consequence:** users lose a familiar working route, focus, or ability to reach content. **Evidence:** ARIA requirements, CSS warnings, and VS Code's explicitly implemented behavior/alternate screen-reader path; no Butter replacement prototype has been evaluated for these. [E5, E7, E10–E11] **Fix:** start with D1; preserve native wheel/keyboard/touch behavior and existing rail buttons. If C is later justified, separately implement and verify keyboard, role/value semantics, focus, pointer cancellation, track behavior, contrast, and target size. A `role="scrollbar"` is appropriate only if it actually controls viewport scrolling; a preview/commit question selector needs semantics matching that operation. Full native parity is a larger commitment than a styled thumb.

### 6. C / D1 — moving denominator and unavailable history

**Conditional — Where:** pointer position mapped to a destination. **Trigger:** older history arrives mid-drag, a new question streams in, an edit changes the branch, or the top of the bar implies unloaded history is already available. **Consequence:** the same pointer position selects another item, release lands at the wrong question, or an impossible preview is promised. **Evidence:** the rail clears position estimates when earlier pages arrive, reindexes questions, and limits earlier-page travel to 50 batches/60 seconds; hold delays request starts but not in-flight responses. [L0, L4] **Fix:** snapshot the loaded ordered IDs at drag start, retain the selected ID instead of its slot, cancel on conversation/branch invalidation, expose an explicit “earlier history not loaded” boundary, and keep pagination a deliberate commitment. Reconcile changed geometry on release. Snapshotting makes selection stable; it cannot provide data that has not arrived.

### 7. B — fallback and residual work cap goal attainment

**Verified — Where:** the hook accelerates remembered layout only. **Trigger:** a never-measured destination or a cache hit with expensive DOM creation/style/paint. **Consequence:** cold stalls survive; warm worst-frame median still exceeds one second; cold blank time can worsen. **Evidence:** audit table and cold missing-coverage run; the defer-ref experiment still had roughly-second frames after removing slow native width reads. [L3] **Trade-off — Fix:** define a narrower partial-benefit target and justify B against that, or pursue upstream rendering granularity. Increasing retention or substituting arbitrary fallback heights is not a supported cure. Reject B if the only acceptance claim remains “snappy continuous native drag.”

### 8. B / D2 / D4 — streaming regression and global-hook cost

**Conditional — Where:** per-block selector publication, observers, prototype getter path, or retained active nodes. **Trigger:** each streaming update invalidates more style rules/DOM or repeatedly enters new page-world work. **Consequence:** Butter's main benefit regresses even when the scrollbar is idle. **Verified evidence:** v1 generated-rule regression, inert selector ablation, and active-only retention regression. The best getter preserves original native return values, but wraps every `Element.clientWidth` access before its filter; it is not the same dependency as Butter's exact smoother callback. [L0, L2–L3, L5–L6] **Fix:** avoid generated selector growth and retention; maintain independent seen marking; bound numeric caches and observer lifetimes. Measure idle streaming and simultaneous streaming-plus-scrub/drag. The existing three-run B result is encouraging evidence, not a universal safety guarantee.

### 9. A — known residual debt, including hold release

**Verified — Where:** the hold only delays initiation of earlier-history GETs; it does not change the virtualizer. **Trigger:** native dragging through already loaded unmounted turns, a request already in flight, or releasing after a queued request. **Consequence:** remount/rollback persists; an in-flight page can still arrive; release incurs insertion work. **Evidence:** frozen hold source and report, including its 30-second safety release and measured release tasks. [L4] **Trade-off — Fix:** keep the feature's claim scoped to deferring request starts, communicate that rail navigation is the alternative for large travel, and retain normal streaming/release checks. Do not promise that alpha.9 solves the native scrollbar. This residual limitation is why A's native-drag score remains low.

### 10. D3 — optimizing the wrong side of the renderer boundary

**Conditional — Where:** replacing KaTeX with snapshots, stripping accessibility MathML, moving arbitrary DOM off-thread, or trying to subdivide ChatGPT's answer from a content script. **Trigger:** React remounts/reconciles, users select/copy math, zoom or theme changes, or assistive tools inspect the answer. **Consequence:** stale visuals, altered mathematical interaction/accessibility, extra duplicate memory, or reconciliation conflict. **Verified evidence:** local traces include substantial DOM/property application/removal outside native layout, and already-rendered KaTeX markup is recreated with no height drift. The cheaper getter still leaves that work. [L1, L3] **Unverified:** no tested Butter-owned alternative math renderer/snapshot or safe React-compatible block subdivision exists in these artifacts. **Fix:** upstream block-level virtualization and deferred measurement, where renderer ownership exists; keep an extension experiment off the release path until it proves content fidelity and speed. CSS can reduce rendering work; it cannot stop React creating nodes it requests.

### 11. D5 — correct long-term target, uncertain delivery

**Trade-off — Where:** upstream request for smaller virtualization units and eliminating synchronous deep measurement. **Trigger:** OpenAI does not prioritize the report or changes the implementation first. **Consequence:** no immediate user relief. **Verified evidence:** saved private call sites and traces provide a specific repro target; the external cases demonstrate mechanisms, not OpenAI's plans. [L1–L3, E1–E8] **Fix:** prepare a minimal public synthetic math chat/repro with a trace showing the commit-time read and large per-turn DOM, then submit only if authorized. No upstream contact was made in this task; there is no claimed support commitment.

## Scores

Scores are engineering judgments about the **current release decision**, not experimental measurements or probabilities. “Navigation” includes finding and reading a destination; “native drag” specifically means continuous actual-content native-thumb travel. ## Recommendation, first action, and re-evaluation

**Trade-off — One recommendation:** adopt **A for the release**, with an explicit boundary around native-drag claims. Do not add B, native-thumb replacement, or extra retention to that release on the present evidence. Keep the alpha.9 hold as the narrowly scoped pagination improvement described by the prompt; verify the actual release build through its ordinary checks because this checkout is older. Treat D1 as the next decision experiment, not as an implementation commitment or a second shipping recommendation.

**Conditional — First action after this research:** review a mockup of an **additive rail scrub** with the user before any visible implementation. The decisive product test is whether preview/commit solves their actual retrieval tasks despite the final wait. If it fails that test, stop there and retain A. This report contains no frontend change or proposed approved design.

**Conditional — Small experiment that could flip the ranking:** after mockup approval and separate lab authorization, use a throwaway additive rail gesture on one fully loaded chat. During hold, snapshot question IDs and update only the preview; issue no ChatGPT scroll writes or destination remount requests. On release, invoke existing rail navigation once for the selected ID. Instrument internal scroll writes, mount commits, main-thread work, preview input-to-paint, and release-to-readable/aligned target. No height getter or retention change in this first comparison; otherwise the sources of benefit cannot be separated.

**Trade-off — Scope the experiment to the decision:**

1. **Conditional:** use paired A/D1 trials with alternating order for a cold destination, a warmed destination, reversal during drag, and a canceled drag. Confirm the target by stable identity, not array index. Repeat enough pairs to distinguish the effect from the observed run variation; three runs are a screen, not a strict safety guarantee.
2. **Conditional:** include the existing recorded streaming replay with typing, plus a scrub while streaming. Require the exact replay output/chunk fingerprint, no target renders attributable to preview while held, and unchanged ordinary wheel/keyboard input. Measure the whole release/recovery window, not just input submission or animation frames during hold.
3. **Trade-off:** proposed gates are preview p95 latency at most 100 ms with no preview stall above 250 ms in the screened states; streaming blocking and worst-key results within a predeclared 10% screening margin of paired A, without a new second-scale stall. These are **decision thresholds**, not a claim that 10% degradation fulfills the final no-regression requirement. If near the margin, gather additional pairs and inspect causes before promotion; final acceptance still requires no meaningful user-visible streaming regression.
4. **Conditional:** release-to-readable target must be no worse than the paired existing rail route, with the original viewport retained during preview and visible pending feedback/cancellation during final work. A short after-release pause is not automatically acceptable: the user must successfully find a known question and an uncertain visual target. Include a halfway-through-long-answer task to expose D1's coverage limit.
5. **Conditional:** only after the full-history screen succeeds, add an in-flight earlier page, unloaded-history boundary, conversation switch, width change, focus loss, outside-window release, reduced motion, keyboard access and one assistive-technology pass. Use the existing fail-closed replay safeguards; do not send real messages. Native overlay/RTL platform coverage is needed before any later C replacement, not assumed from D1's success.

**Trade-off — Re-evaluate A when:** D1 meets those gates and the user chooses its interaction; the user's real task demands continuous within-answer scrubbing; ChatGPT exposes a supported navigation/renderer seam; an upstream release changes virtualization or removes the forced read; or representative hardware/chats reverse the measured trade-off. Reconsider B only for a clearly valued partial latency target and after synchronous content-width/owner safety is demonstrated. Test B against D1 **after** D1 succeeds, and keep it only if it materially improves final readiness beyond its maintenance/risk cost. Better cold cache collection alone cannot explain away the warm second-scale residual.

**Unverified — Remaining gaps:** no primary source inspected proves ChatGPT internally uses TanStack, Virtuoso, or Monaco; no claim is made about Slack/Discord/Telegram/Google Docs internals. No real C/D1 implementation, user acceptance result, cross-platform native interception proof, combined B/C benchmark, or alpha.9 release audit exists in this assessment. These gaps are why the evidence supports a bounded experiment rather than a replacement-scrollbar promise.
