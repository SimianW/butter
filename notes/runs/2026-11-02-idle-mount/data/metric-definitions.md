# Metric definitions and limits

- **Task:** Long Tasks API entry duration. Zero reported max means no entry over the API's 50 ms threshold, not zero work. The background acceptance gate is absolute max task at most 100 ms, with 50 ms as the stretch target.
- **LoAF:** Long Animation Frames API entry duration, including script and rendering. Blocking sums `blockingDuration`; it is not total elapsed time. A sequence of smaller tasks can still create a long frame. Maximum task, maximum LoAF and frame interval are separate metrics.
- **Worst frame:** maximum recorded rAF timestamp interval, including recovery after native release. This is not a compositor presentation trace for every refresh.
- **Blank hold:** prior central low-ink screencast heuristic, weighted by presentation timestamp duration. It is not a GPU missing-tile count. Partial content and ordinary whitespace can resemble each other. The MP4s and contact sheets are the visual evidence.
- **Typing:** CDP event timestamp at submission through rAF plus a queued task. This includes waiting for a busy main thread and approximates key-to-paint; it is not a photodiode presentation measurement. Wheel acknowledgment is driver latency, while the recorded frame series shows concurrent growth stalls.
- **Cold growth:** complete assembled server entries with incomplete measured heights. All available entries are present, but geometry can still begin as estimates. Initial and final height are retained. This is explicitly different from the calibrated drag setup.
- **Calibrated drag:** complete 12-entry history, two full traversals, a start near scrollTop 1800, visible scroller, genuine native minimum-thumb press. Fast input is 60 steps over a requested 1.2 s; slow input is 120 over 12 s. Inputs can queue behind stalls.
- **Controlled growth time:** forced one-turn requests with the same inter-step schedule, for commit attribution. **Real idle growth time** uses the prototype's visible/stream/input gate and default idle interval. Do not substitute one for the other.
- **Streaming:** unchanged original 189-chunk, roughly 122-second schedule. Full hash and chunk count are required. Final quiet-arm regrowth is recorded after the streaming metric window; it does not inflate the reported ordinary streaming total.
- **Boundary windows:** two-second windows around observed send and stream-end events can include ordinary initial/final answer work. The separate lifecycle phase isolates mode toggles without an answer. A zero boundary LoAF means no observed over-threshold frame, not instantaneous work.
- **Memory:** forced-GC Runtime.getHeapUsage and DOM counters, plus connected active-element counts. Memory includes renderer caches and instrumentation, not only the feature allocator. The broad scroll probe observes removed turns, so its later DOM counters can include retained observer targets. The standalone chat-switch probe avoids that probe. The growth pairing adds connected turns without eviction and is the cleaner retention measurement.
- **Bounds:** final prototype limits 24 available turns and a projected 300,000 active elements with a 50,000-element reserve. Earlier main measurements used 260,000; both admit this 12-turn chat. The final cap also admits its 13-turn replayed answer. This is a conservative soft node budget, not a hard byte-memory guarantee or a limit on one enormous native answer.
- **Repeated samples:** medians are of run-level values; ranges are observed minima/maxima. Small sequential samples on one software-rendered Linux Chromium lab establish these failures and tradeoffs, not statistical significance or universal device performance.

The native schedule traverses the full long history to the bottom region, but minimum-thumb grab offset/rounding can leave a run slightly short of the exact maximum scrollTop. Per-run start/end/remaining pixels are saved in drag-endpoints.json; the selected retained slow repetition ends 356 px short. It is kept and disclosed, not relabeled as an exact-bottom assertion.
